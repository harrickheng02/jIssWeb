## Context

论坛数据与 API 已在 `JIssWeb.Model.Api` 落地；身份以 JWT `sub` 为准（`token-identity-consistency`）。pm-plan M2 要求站内通知最小闭环，依赖已归档的用户键一致性约定。

## Goals / Non-Goals

**Goals:**

- Mongo 持久化通知；仅站内消费；收件人键为 `RecipientSubId`，与 user-service / JWT `sub` 字符串一致。
- 最小事件：**帖子被他人回复**时向**帖子作者**投递一条通知（作者自回复不产生）。
- 当前用户分页列表、未读筛选或标记、单条/全部已读；前端列表空态与请求失败态。
- 顶栏登录态下可进入通知列表。

**Non-Goals:**

- 邮件/WebSocket/多端推送矩阵。
- 复杂 @ 解析与富文本（若后续做 @，需单独变更）。
- 站内信会话与回复链。

## Decisions

1. **存放位置**：通知与帖子/回复同属 Model 服务 Mongo，避免跨服务事务。**一致性验收**以 `tasks.md` 2.3 为准：同一 HTTP 请求内顺序写入（回复 → 更新帖子评论数 → 插入通知）；通知插入失败则该请求失败；未使用 Mongo 多文档事务（单机/开发环境常见无副本集）。若需多文档事务，需副本集并另开变更。
2. **事件范围**：首版仅 `REPLY_TO_POST`；`MENTION` 不纳入本变更验收（与 pm-plan「至少一种事件」一致）。
3. **API 前缀**：`GET/PATCH` 类路由挂在 `/api/forum/notifications`，与现有 `/api/forum/*` 一致，且全部走 JWT 用户范围（无匿名列表）。
4. **分页**：与帖子列表一致采用 `page` + `pageSize`（或项目既有统一分页参数名），默认按创建时间倒序。
5. **已读模型**：服务端存 `ReadAt == null` 为未读；`PATCH .../read` 与 `POST .../read-all` 幂等。
6. **幂等与重复**：同一回复若重复提交创建（重试），依赖实现可选用 `ReplyId` 唯一索引去重或接受极小概率重复（任务阶段定稿）。

## Risks / Trade-offs

- **[Risk]** 非多文档事务下，顺序写若在「回复已落库之后、通知插入之前」发生进程级异常，理论上可能出现短暂不一致 → **Mitigation**：通知插入失败则请求失败；重复通知依赖 `ReplyId` 唯一索引与捕获 11000；更强一致性需副本集 + Session 事务（另变更）。
- **[Risk]** 无实时推送，用户需打开列表 → **Mitigation**：M2 验收为站内闭环，非目标已排除实时通道。
- **[Trade-off]** 未读数轮询 vs 首屏带在用户信息 → 首版可在进入列表时拉取列表与未读计数（或从列表推导），不强制顶栏实时数字。

## Migration Plan

- 新增集合与索引；无存量数据回填。
- 部署顺序：先后端与索引，再前端；回滚时停用路由与 UI，旧数据可保留。
