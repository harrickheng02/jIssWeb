## Why

邮箱验证成功后仍要求用户再去登录页输入密码，步骤重复、流失高。应在验证成功时直接建立会话（发放访问/刷新令牌或等价会话），让用户无感进入已登录状态。

## What Changes

- 验证成功响应（或重定向携带）中建立与用户登录等价的会话：签发访问令牌与刷新令牌（或项目既定会话模型）。
- 前端验证成功路由：收到令牌后写入既有客户端状态/存储，跳转到业务首页或原目标，而非强制登录页。
- 保持签名、一次性消费、限流与滥用防护不变；不削弱验证链路的防重放与过期约束。

## Capabilities

### New Capabilities

（无独立新能力域；行为在既有能力上扩展。）

### Modified Capabilities

- `email-verification-registration`：验证完成端点在成功时除更新已验证状态外，须允许客户端获得正常受保护 API 可用的访问/刷新令牌（或文档化的等价会话），并与「仅已验证账号可获完整会话」一致。
- `user-service`：验证完成路径上的令牌签发规则与登录一致（`sub`/claims、刷新策略），且错误与限流语义保持稳定可区分。
- `frontend-app-shell`：验证成功页在拿到令牌后进入已登录壳层（或约定落地页），不再将「去登录页」作为唯一成功路径。

## Impact

- `JIssWeb.User.Api`：验证相关 handler、可能的响应 DTO/重定向参数。
- 前端：验证回调/成功路由、Pinia/存储写入、路由守卫与 `clients.ts` 一类 HTTP 客户端。
- 与现有 remember-me、刷新、网关/BFF 无冲突前提下对齐 Cookie/Header 或 body 传 token 的既有约定。
