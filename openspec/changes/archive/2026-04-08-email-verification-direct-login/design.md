## Context

当前流程：用户点击邮件链接 → 服务端校验 → 标记邮箱已验证 → 前端成功页再跳转登录。与「验证即身份确认」重复，体验差。

## Goals / Non-Goals

**Goals:**

- 验证成功当次请求内建立与登录等价的会话（访问令牌 + 刷新令牌，与现有登录响应字段/存储约定一致）。
- SPA 在成功路由上写入令牌并进入已登录壳层或约定首页，无需再输入密码。
- 不改变签名、一次性消费、限流与错误码可区分性。

**Non-Goals:**

- 第三方 OAuth、无密码 magic link 全站改造。
- 修改 JWT 结构或引入全新会话协议（除非实现时发现与登录无法对齐）。

## Decisions

1. **令牌来源与登录一致**  
   复用现有登录签发逻辑（同一 `TokenService`/刷新会话创建路径），在验证 handler 内于「标记已验证」之后调用，保证 `sub`、过期、刷新轮换与登录一致。

2. **传输形态**  
   优先：JSON API 响应体返回 `accessToken`/`refreshToken`（或与登录相同 DTO），由前端成功页写入 store。若当前为浏览器重定向到带 query 的 SPA：在任务中二选一并与现有网关/CORS 一致；避免长期把 refresh token 放在 URL。

3. **与「未验证前不发完整会话」兼容**  
   仅在验证 artifact 校验通过且即将/已经标记 `EmailVerified` 后签发；此前仍不发完整业务会话。

4. **Remember-me**  
   若登录页有 remember-me，验证成功路径采用与登录成功相同的持久化策略（或文档化默认等价于「记住」），避免两套存储行为。

## Risks / Trade-offs

- 验证链接若被中间人截获单次使用仍有效至消费 → 与现有一次性令牌一致；须保持 HTTPS 与短 TTL。  
- 重定向带 token 泄露风险 → Mitigation：优先 body/POST 交换或 fragment，任务中明确禁止或限时 query 中的 refresh。

## Migration Plan

- 先上后端再上前端：后端先返回令牌时旧前端可忽略仍去登录；新前端依赖新字段。  
- 回滚：特性开关关闭时恢复「仅成功提示 + 跳转登录」。

## Open Questions

- 当前验证完成是 API JSON 还是 302 到前端路由：以代码为准在任务中固定一种主路径。
