## Context

当前系统已有基础登录/注册流程，但认证页更多偏向开发验证入口，缺少稳定的页面信息层次、按钮状态、统一错误反馈、移动端约束与安全协同说明。用户希望把认证页定义为正式业务入口：居中卡片式布局、登录/注册切换、行内校验、忘记密码/第三方登录预留、协议与隐私链接、以及与后端配合的失败限制与验证码触发机制。

该变更横跨前端认证页体验与 User 服务的错误反馈/安全控制，因此需要先明确页面边界和前后端职责。

## Goals / Non-Goals

**Goals:**
- 定义统一的登录 / 注册页布局，包括 header、核心表单、footer、卡片尺寸与响应式行为。
- 约束登录态与注册态字段、按钮、切换方式、focus/blur 反馈、实时校验、行内错误提示与 loading/disabled 状态。
- 规定「忘记密码」「第三方登录」在页面上的入口或预留位置，避免未来再做结构性重排。
- 要求 User 服务返回可区分的认证失败反馈，并支持登录失败限制、验证码触发或等价风控升级机制。
- 保持低认知成本：主路径短、反馈明确、移动端易点按。

**Non-Goals:**
- 不在本变更中强制实现完整的第三方登录闭环。
- 不在本变更中强制实现完整的找回密码邮件 / 短信流程。
- 不定义完整品牌视觉系统，仅给出认证页所需的最小 UI 规范。

## Decisions

1. **布局采用居中单卡片**
   - 认证页统一使用居中 Card，桌面端强调聚焦，移动端允许卡片贴边缩窄。
   - 相比整页分栏或大面积营销头图，单卡片更适合当前产品阶段，认知负担更低。

2. **登录 / 注册采用同页 Tab 切换**
   - 使用同一页面内 Tab 保持上下文一致，减少跳页成本。
   - 过渡动画可以是淡入或轻量滑动，但不把动画作为实现前提。

3. **错误提示以行内为主、顶部提示为辅**
   - 输入合法性错误优先显示在输入框下方红字。
   - 请求级错误可同时配合顶部 alert / toast，但不能替代行内提示。
   - 这样既能明确定位字段，又能保留全局失败反馈能力。

4. **前端做即时校验，后端做最终兜底**
   - 邮箱格式、密码长度、确认密码、协议勾选、是否填写完整由前端即时提示。
   - 登录失败次数限制、验证码触发、防暴力破解与稳定错误码由后端负责。
   - 这样可以兼顾体验与安全，不把安全判断下放给前端。

5. **忘记密码 / 第三方登录先做入口预留**
   - 第一阶段只要求页面结构支持入口区域与占位，不强制后端闭环。
   - 这样能先稳定信息架构，同时避免把本次范围扩成完整认证体系重构。

6. **响应式优先以表单可用性为标准**
   - 移动端关注输入框宽度、按钮高度、点击区域、tab 可读性与 footer 可折行。
   - 视觉规范采用低门槛参数：标题 16~20px、输入 14~16px、卡片圆角 8~16px、输入圆角 6~10px。

## Risks / Trade-offs

- **[风险] 页面能力先于后端能力上线** → 前端把忘记密码/第三方登录实现为禁用态或“即将开放”入口，避免误导用户。
- **[风险] 实时校验过于频繁造成打扰** → 优先使用 blur 触发和提交时兜底，必要时对输入中校验做节流。
- **[风险] 登录失败限制导致误伤正常用户** → User 服务返回稳定错误码，并区分普通失败与限流/验证码升级状态。
- **[风险] 认证页承担太多附加信息导致拥挤** → header/footer 信息保持轻量，把主操作区优先让给登录/注册表单。

## Migration Plan

1. 在前端整理现有认证页为统一 Auth Page 结构。
2. 补充 User 服务可识别的错误码、失败次数限制与验证码触发语义。
3. 分阶段接入忘记密码与第三方登录真实流程；未完成前保留入口占位。
4. 发布后用移动端与桌面端分别进行人工走查。

## Open Questions

- 登录主标识最终是否只展示邮箱，还是保留“用户名 / 邮箱 / 手机号”的统一文案入口。
- 注册阶段验证码是邮箱验证码、短信验证码，还是仅在风控升级时触发。
- 忘记密码与第三方登录入口在首版是显示可点击占位，还是完全隐藏直到后端准备好。
