## 背景

- 登录/注册与邮箱验证已在 user-service 与 SPA 落地；`ForgotPasswordView` 仍为占位。
- 邮件基础设施（模板、SMTP 或抽象）可与邮箱验证共用模式；密码重置须使用**独立签名密钥与配置前缀**，避免与验证链接混用。
- JWT 与 refresh 轮换、Redis 黑名单或会话存储已在既有设计中存在，重置成功后的会话发放应复用同一签发路径。

## 目标 / 非目标

**目标：**

- 邮箱发起重置 → 邮件内安全链接 → 用户设新密码 → **立即获得与登录一致的会话**（access/refresh），减少再登录步骤。
- **防用户枚举**：接口层统一响应文案；内部限流（IP、规范化邮箱维度）。
- 重置令牌：**短 TTL**、**单次使用**；校验失败时稳定、可区分的错误码（过期、已使用、格式无效）。
- 重置成功后 **吊销该用户既有 refresh 会话**（或等价策略），使旧设备上的 refresh 失效，同时当前完成重置的客户端持有新会话。

**非目标：**

- 短信、MFA、人工审核。
- 管理员代重置。

## 决策

1. **链接形态（推荐与验证邮件对齐）**  
   - **选项 A**：邮件指向 **后端 GET**，校验签名与一次性规则后 **302** 到前端 `/auth/reset` 并携带**短期 exchange**（query 或 fragment），前端再调 API 换会话并展示设密表单。  
   - **选项 B**：邮件直接指向前端 `/auth/reset?token=…`，提交新密码时由后端校验 opaque token。  
   **选择**：优先 **A**（敏感凭证经服务端跳转与短期 code，减少 token 长期留在地址栏与 Referrer 风险）；若工期紧可采用 **B** 但须 HTTPS、短 TTL（仍靠后端校验）。  
   **记录**：在实现 tasks 中择一写死，并在配置中明确 `PasswordReset__*` 与 `EmailVerification__*` 分离。

2. **防枚举**  
   - 请求重置接口无论邮箱是否存在均返回**相同**成功语义；耗时可做轻微归一化（可选）。  
   - 未注册邮箱不发邮件，仅审计日志。

3. **成功后会话**  
   - 与 `user-service` 登录成功路径一致签发 claims；调用现有 refresh 吊销/轮换逻辑，**使该用户其他 refresh 全部失效**（或按设备策略，默认全吊销更安全）。

4. **限流**  
   - 与登录、验证重发类似：按 IP、按邮箱分桶；超限返回与 user-service 一致的机器可读结果供前端提示。

## 风险与权衡

- **[风险]** 统一成功文案可能被用于探测「是否发信」（邮件延迟差异）。  
  **缓解**：限流 + 监控异常 IP；不承诺邮件秒达。
- **[风险]** 全量吊销 refresh 导致其他设备立即登出。  
  **缓解**：与「改密后踢掉其他会话」安全预期一致；可在后续变更引入设备列表。

## 迁移与上线

- 新配置项默认值在开发环境可用；生产需设置密钥与外链基址。  
- 无存量数据迁移；可选为 Redis 键前缀新增 `pwdreset:`。
