## Context

JIssWeb 当前以前端直连多后端服务为主，开发环境通过 Vite 代理把 `/api-user`、`/api-customer` 等前缀映射到不同端口。该方式适合早期开发，但随着后续引入 Cloudflare、Nginx、更多业务服务、统一认证治理、前端聚合接口与生产负载分流，现有拓扑缺少统一入口与前端编排层。

目标架构链路为：

Cloudflare → Nginx → YARP API Gateway → ASP.NET Core BFF → 业务服务

其中：
- **Nginx** 负责外层反向代理、TLS、基础负载均衡与静态资源入口
- **YARP** 负责服务路由、头透传、统一流量治理
- **BFF** 负责前端专属接口聚合、响应整形与页面级编排
- **业务服务** 保持领域逻辑与数据访问职责

## Goals / Non-Goals

**Goals:**
- 为仓库增加 YARP 网关与 BFF 的基础骨架，明确进程角色和接口边界。
- 统一前端 API 入口，逐步摆脱前端直接感知所有后端服务前缀的模式。
- 规定 Cloudflare / Nginx / YARP / BFF / 业务服务的职责切分，避免层间重复。
- 为本地开发、Docker 网络和未来生产部署提供一致的路由与连接规范。
- 为后续统一认证、限流、熔断、灰度、观测和前端聚合接口提供可扩展落点。

**Non-Goals:**
- 不在本变更中实现完整的生产级服务发现平台。
- 不在本变更中完成所有业务页面的 BFF 聚合改造。
- 不在本变更中强制引入完整的 Nginx/Cloudflare 生产配置文件。
- 不把 BFF 做成第二个通用网关，不让业务服务承担前端编排。

## Decisions

1. **YARP 与 BFF 分层**
   - YARP 只做路由与流量治理，不承担页面聚合逻辑。
   - BFF 只提供面向前端的聚合与整形接口，不承担通用服务发现职责。
   - 这样避免“网关”和“BFF”双重转发层同时变成业务代码堆积点。

2. **前端对外收口到统一入口**
   - 前端未来只感知一个统一 API 域或统一前缀。
   - 业务服务地址、端口、路径重写由 YARP/BFF 处理。
   - 这样可以降低前端与服务拓扑耦合。

3. **认证采用透传 + 服务保底校验**
   - YARP / BFF 可以做认证前置处理与上下文透传，但业务服务仍保留 JWT 保底校验。
   - 这样避免单点网关失误导致内部服务裸奔。

4. **Docker 与宿主机都支持**
   - 本地开发允许网关/BFF 跑在宿主机、依赖在 Docker。
   - 容器化运行允许所有组件通过 Compose 服务名互联。
   - 这样兼容当前开发习惯与未来部署模式。

5. **迁移分阶段**
   - 第一步先建立 YARP 和 BFF 的项目与最小路由。
   - 第二步让前端认证与基础业务调用切到统一入口。
   - 第三步再逐步做接口聚合、错误码整形、限流与观测增强。

## Risks / Trade-offs

- **[风险] YARP 与 BFF 职责混淆** → 在 specs 中明确：YARP 不写页面聚合，BFF 不做通用网关。
- **[风险] 多一层转发带来延迟和调试复杂度** → 初期只落最小路由与少量聚合接口，并补充清晰日志链路。
- **[风险] 前端迁移期接口双轨并存** → 采用渐进式迁移，保留旧入口短期兼容窗口。
- **[风险] Nginx 与 YARP 路由重复配置** → 外层 Nginx 仅做入口级职责，服务级转发规则收口到 YARP。

## Migration Plan

1. 新增 YARP Gateway 项目与 BFF 项目，打通到至少一个现有业务服务。
2. 在 Compose 与本地文档中加入网关/BFF 运行方式和连接变量。
3. 前端将认证与至少一个业务域接口改为统一入口访问。
4. 验证路由、认证透传、容器网络与宿主机网络模式。
5. 后续再把更多业务接口迁入 BFF/网关路径。

## Open Questions

- BFF 是单独对前端统一开放一个服务，还是按端（Web / Mobile / Admin）分多个 BFF。
- 网关是否首期就引入限流、熔断、重试策略，还是只先做最小转发。
- 前端旧的 `/api-user`、`/api-customer` 前缀是立即废弃还是短期保留兼容。
