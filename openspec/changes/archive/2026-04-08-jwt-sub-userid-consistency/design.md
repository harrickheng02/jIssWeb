## Context

当前项目为多服务 JWT 鉴权骨架，服务间都会从令牌中提取用户标识。若 `sub` 与 `userId` 并存且未强制一致，不同服务按不同字段解析会产生权限漂移与审计歧义。该变更需要在登录与刷新令牌流程中统一身份主键语义，并给出跨服务统一失败策略。

## Goals / Non-Goals

**Goals:**

- 统一身份主键优先级：`sub` 为唯一主标识。
- 保留 `userId` 业务语义字段时，强制 `userId == sub`。
- 在 access/refresh 令牌签发与校验链路中保证标识不漂移。
- 规定资源服务在检测到不一致声明时的统一失败语义。

**Non-Goals:**

- 不在本设计中扩展多角色/RBAC 体系。
- 不在本设计中引入第三方 IdP 或 OAuth 社交登录。
- 不改变现有 JWT 算法与基础配置模型（issuer/audience/signing key）。

## Decisions

1. 身份主键规范
   - 决策：`sub` 作为跨服务唯一用户标识，资源服务必须优先读取 `sub`。
   - 保留：允许同时存在 `userId`，但其为语义增强字段，不可独立于 `sub`。
   - 约束：签发端若写入 `userId`，必须与 `sub` 完全一致（字节级字符串一致）。
   - 备选方案：仅保留 `userId` 不使用 `sub`。未采用原因：偏离 JWT 通用语义，跨库/中间件兼容性较差。

2. 令牌签发与刷新一致性
   - 决策：登录签发 access/refresh 时写入同一用户主键；刷新流程从已验证 refresh 会话中取主键并重新签发，禁止客户端自报主键。
   - 备选方案：刷新时允许客户端传 userId 并比对。未采用原因：增加攻击面与分支复杂度。

3. 资源服务校验失败语义
   - 决策：若 token 内 `sub` 缺失，或 `userId` 存在但不等于 `sub`，统一按无效令牌处理（401）。
   - 备选方案：忽略 `userId` 不一致继续放行。未采用原因：会掩盖签发端缺陷并造成审计风险。

4. Redis 黑名单与刷新令牌协同
   - 决策：一期即采用 refresh token + Redis 黑名单模型；黑名单校验通过后才允许刷新签发。
   - 约束：被吊销 refresh 对应会话不得再生成新 access。
   - 备选方案：先不做黑名单。未采用原因：后续补齐会引发令牌生命周期重构。

## Risks / Trade-offs

- [风险] 历史/外部 token 仅含 `sub` 或字段命名不一致 → [缓解] 明确兼容规则：`userId` 可选，但出现时必须等于 `sub`。
- [风险] 多服务各自写解析逻辑导致行为不一致 → [缓解] 在 shared-foundation 统一声明解析与失败语义。
- [风险] 刷新与黑名单路径增加 Redis 依赖 → [缓解] 规范超时、降级与错误码，确保故障时默认拒绝刷新而非放行。
- [权衡] 保留 `userId` 增强可读性，但增加一致性校验开销 → [缓解] 仅做简单字符串一致校验，复杂度可控。

## Migration Plan

1. 在 user-service 与 shared-foundation 规格中落地 `sub` 主标识与 `userId==sub` 约束。
2. 实现期先改签发端，再改资源服务校验端，避免先收紧校验导致现网 token 全量失效。
3. 切换期间允许仅含 `sub` 的 token，通过后逐步要求新签发 token 同时携带一致 `userId`（若业务需要保留该字段）。
4. 回滚策略：仅回滚一致性强校验，保留 `sub` 主标识语义不回滚。

## Open Questions

- `userId` 是否在一期默认下发，还是按客户端需求按需下发。
- 刷新令牌的会话粒度（按设备、按客户端、或按用户全局）如何定义。
